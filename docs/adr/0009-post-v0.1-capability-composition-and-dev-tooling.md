# ADR 0009: Post-v0.1 capability composition and dev-only tooling

- Status: Accepted
- Date: 2026-07-28

## Context

Version 0.1 registers capabilities as a plain map passed to `createEngine`.
Reusing a capability across engines currently means copying its handler or
spreading two maps together at the composition root. Object spread silently
overwrites a duplicate key: the last declaration wins, the previous capability
disappears from `list`, `describe`, the CLI, and MCP, and nothing fails. Once a
capability is published by a local ESM module or a community package, that
silent overwrite stops being a typo and becomes a correctness and security
defect, because the surviving handler may carry a different access rule than the
one the engine author believed was registered.

The evolution trigger for this work is already recorded in
`docs/scope-matrix.md`: ownership metadata is considered only when object spread
no longer addresses real ownership. Reusable atomic ESM exports and versioned
capability libraries are that case.

The conventional answer to reuse is a plugin system with discovery,
registration, and initialization hooks. That is exactly what ADR 0001 rejected,
and `docs/v0.1-scope.md` fixes containers, modules, and plugins at zero. A
decision is therefore required before any implementation, both to authorize the
addition and to bound it so that it cannot grow into the runtime module system
ADR 0001 forbids.

`docs/specs/capability-libraries-and-composition.md` is the normative
specification for the resulting behavior, requirements, and acceptance criteria.
This ADR records the architectural decision and its cost, not the requirement
detail.

## Decision

`@ai-engine/core` will gain an additive, eager, immutable capability composition
API after v0.1, and the repository will gain one development-time package that
provides the authoritative build gate for it.

The composition API ships after v0.1 and targets version `0.2.0`. It does not
retroactively change the v0.1 contract. `createEngine` keeps accepting a plain
capability map, so every existing engine remains valid without modification; an
engine claims the guarantees below only by composing through
`composeCapabilities`. The v0.1 primitives, five required capability fields, six
pipeline stages, seven error codes, and single `onEvent` hook are unchanged.

### An eager composition descriptor is not a runtime module system

ADR 0001 remains in force and is not amended. This decision introduces no
package registry, service locator, dependency injection container, lifecycle
manager, registration decorator, discovery through reflection, hot loading,
file-system or remote scanning, and no `modules` system with initialization
hooks. Specifically:

- `composeCapabilities` is a pure, synchronous, side-effect-free function. It
  performs no I/O, starts no adapter, never calls `run` or an access rule, and
  completes before `createEngine` is called.
- Its inputs are values the application imported explicitly with ESM `import`.
  Node and the host package manager remain responsible for module and package
  resolution; the framework operates only on the value it is handed
  (`AE-LIB-01`, `AE-EXPORT-03`).
- Its output is the same `CapabilityMap` that `createEngine` already accepts.
  There is no second registration path, no framework-owned mutable state, and
  no global into which a module can register itself.
- Capability dependencies still enter through factories and custom-engine ports
  at the application composition boundary (`AE-EXPORT-05`, `AE-LIB-04`). An
  exported capability MUST NOT acquire dependencies from `ExecutionContext`, a
  global registry, or a framework service locator.
- An exported capability or library MUST NOT start or configure an official
  adapter as a side effect of definition or import (`AE-LIB-05`,
  `AE-EXPORT-07`).
- Imported capabilities execute through the single `engine.invoke` pipeline of
  ADR 0003, with the adapter convergence required by ADR 0005. Importing adds no
  stage, no hook, and no execution path.

The composition API is therefore a typed constructor for a value the v0.1 kernel
already accepts, not a runtime for loading code. Dependencies still point from
the boundaries toward the core, and initialization order remains visible in the
composition root.

### Collision safety is a construction-time invariant

Composition has no precedence, no last-write-wins or first-write-wins, no
priority, and no identity deduplication. Declaration order, import order, source
or library version, and object identity MUST NOT resolve a duplicate
(`AE-COLLISION-02`). Every detectable duplicate effective ID — across local
declarations, atomic imports, library imports, default IDs, atomic `as` targets,
and library `remap` targets — MUST fail composition synchronously, before
`createEngine` returns and before any adapter can listen (`AE-COLLISION-01`,
`AE-COLLISION-03`). Importing the same exported value twice under the same
effective ID is a collision, not a tolerated repetition. Mounting one capability
under two IDs requires two explicit import descriptors.

One validation pass MUST report every detectable issue, in a deterministic
order, with the effective ID and complete provenance for each conflicting
declaration (`AE-COLLISION-04`, `AE-COLLISION-05`).

An invalid composition throws a `CapabilityCompositionError` that extends
`TypeError` and carries a machine-readable `code` of
`CAPABILITY_COMPOSITION_INVALID` together with an immutable `issues` array.
Tooling and tests MUST use `code` and `issues` and MUST NOT parse the message.

This is a construction error. It does not expand the invocation error taxonomy
fixed by ADR 0003: `EngineError` keeps exactly `CAPABILITY_NOT_FOUND`,
`INPUT_INVALID`, `UNAUTHENTICATED`, `FORBIDDEN`, `OUTPUT_INVALID`, `CANCELLED`,
and `EXECUTION_FAILED`. A composition failure occurs before any invocation
exists, so it has no request ID, no event, and no CLI, MCP, or HTTP mapping. It
belongs to the same construction-time `TypeError` boundary that `createEngine`
already uses to reject invalid configuration.

### Two complementary gates

Collision detection has a best-effort static gate and an authoritative
runtime gate.

When every ID is a literal type, `composeCapabilities` MUST make duplicate
effective IDs, a bare `CapabilityDefinition` passed to `importCapability`,
unknown `include` entries, and unknown or unselected `remap` keys TypeScript
errors, while preserving the inferred `Engine` input and output types
(`AE-EXPORT-06`, `AE-COMP-05`, `AE-COMP-08`).

The static gate alone is insufficient and MUST NOT be presented as the
guarantee. IDs built from configuration, computed maps, values widened to
`string`, and compositions assembled in a loop escape static analysis, and types
are erased before the published code runs. The runtime validation performed by
`composeCapabilities`, and the build gate that executes it over a real module,
are authoritative.

The build gate is `ai-engine check-capabilities <esm-module> [--export <name>]`,
inspecting the `capabilities` export by default. It imports the module without
starting an adapter, verifies that the selected export carries framework
composition provenance, reports every issue in one run as payload-free
diagnostics on `stderr` with no `stdout` output, and exits `0` for a valid
composition, `1` for composition issues, and `2` for invalid usage, a module
load failure, a missing export, or an untracked raw map. It MUST NOT
re-implement validation, invoke a capability, or start a transport. Continuous
integration MUST run it for every engine that composes imported capabilities.

### A fourth, development-only package

ADR 0004 is amended, not superseded. The three runtime product packages
`@ai-engine/core`, `@ai-engine/cli`, and `@ai-engine/mcp` keep their names,
responsibilities, and dependency rules unchanged, and the runtime package count
remains three.

`@ai-engine/tooling` is added at `packages/tooling` as a native ESM,
development-time command-line tool providing `ai-engine check-capabilities`. It
contributes no runtime contract, capability, adapter, or transport. No runtime
package depends on it: the dependency direction is tooling to core only, and
`@ai-engine/core` MUST NOT depend on `@ai-engine/tooling`. Tooling may depend
only on the core's public composition API and Node built-ins.

From `0.2.0` the project therefore publishes four packages while continuing to
ship three runtime packages. The `AE-SCOPE-01` count of three remains the
recorded v0.1 limit; the zero counts for containers, modules, and plugin systems
are unchanged by this decision.

### Composition metadata is diagnostic data, not a trust boundary

An atomic `source.name` and `source.version`, and a library `name` and
`version`, are opaque strings chosen by the author of the imported module. The
framework does not resolve, verify, compare, or semantically interpret them; the
host package manager resolves installed packages (`AE-EXPORT-02`, `AE-LIB-02`).
They are not a sandbox, a permission manifest, a signature, an attestation, or a
supply-chain security mechanism.

An imported atomic export or capability library is executable application code
with the same trust level as any other local or installed dependency. Importing
it grants it everything the host process already has. Reviewing, pinning, and
auditing dependencies remain host responsibilities.

Import and collision diagnostics MUST NOT evaluate `run`, call an access rule,
or serialize dependency values, capability inputs, outputs, schemas, handler
source, or credentials. Only effective IDs, default IDs, and declared provenance
strings may be reported. This matches the payload-free rule ADR 0003 applies to
events and ADR 0005 applies to CLI error output.

### Deferred

The following remain outside this decision, stay unspecified, and require their
own evidence and architectural decision before any implementation: marketplace
discovery and community package indexing; library trust, signing, and permission
declarations; compatibility negotiation between library and engine versions;
transitive library manifests or dependency graphs; automatic aliases or
deprecation redirects for renamed IDs; hot reload and dynamic enablement; and
remote or distributed capability composition.

Delivery follows ADR 0008. Each slice of the specification is a separate
validated, cohesive commit with its own red/green/refactor cycle and its own
acceptance evidence.

## Alternatives considered and rejected

- **Runtime plugin discovery.** Scanning `node_modules`, a manifest, or a
  directory to register capabilities automatically. Rejected: it reintroduces
  the discovery and initialization hooks ADR 0001 forbids, makes the registered
  capability set depend on install state rather than on code, and destroys
  static typing of `invoke`.
- **A dependency injection container.** Resolving capability dependencies from a
  framework-owned container instead of factories. Rejected by ADR 0001;
  factories already express the same wiring with visible order, no global state,
  and no container infrastructure in tests.
- **Automatic ID namespacing.** Prefixing every imported capability with its
  source or library name. Rejected: it hides collisions instead of reporting
  them, makes a public capability ID depend on a string the framework treats as
  opaque diagnostic metadata, and turns the domain-oriented IDs required by
  `AE-INV-01` into package-oriented ones. The importer instead chooses the
  effective ID explicitly with `as` or `remap`.
- **Last-write-wins or priority-based conflict resolution.** Resolving a
  duplicate by declaration order, import order, or a declared priority.
  Rejected: it is precisely the silent object-spread failure this decision
  exists to eliminate, and it makes the surviving access rule a function of
  ordering rather than of an explicit choice.
- **Merging colliding definitions.** Unioning schemas, chaining handlers, or
  combining access rules for a shared ID. Rejected: there is no meaningful merge
  of two handlers or two authorization rules, and the result would break the
  stable contract of `AE-INV-02` and the five-field capability of `AE-CAP-01`.
  Two behaviors require two IDs.
- **The static type gate alone.** Relying only on type-level collision
  detection. Rejected: computed IDs and dynamic maps escape it, and types do not
  exist at runtime.
- **A new `EngineError` code for composition failures.** Rejected: a composition
  failure has no invocation, request ID, event, or transport mapping, and
  extending the seven-code taxonomy would change a contract every adapter and
  integration already depends on.
- **Composing already-created `Engine` instances.** Rejected: it would place a
  second execution path in front of `invoke` and duplicate the ADR 0003
  pipeline.

## Consequences

- Existing v0.1 engines keep working unchanged; adopting composition is opt-in
  and the guarantees apply only to engines that adopt it.
- The core gains type-level collision machinery. Generic signatures become
  harder to read and to maintain, type-checking cost grows with large literal
  compositions, and a collision surfaces as a type error that requires a
  documented reading. The runtime path stays simple, linear, and non-recursive,
  so a 10,000-declaration composition validates without stack overflow
  (`AE-AC-13`).
- A new versioning surface appears. Changing an atomic export's default ID
  breaks importers that did not pin a stable `as` target; changing a library
  default ID is a breaking library change; changing an engine's remap target is
  a breaking engine change because direct, CLI, and MCP consumers observe the
  effective ID. Changing only diagnostic source metadata does not change the
  execution contract but may change tooling diagnostics and stored baselines.
- The collision guarantee is bounded by provenance. A map already flattened
  through raw object spread has lost its source boundaries, so composition can
  no longer observe the overwrite. Documentation MUST NOT present raw spread as
  safe composition, and the build checker MUST reject an unbranded,
  already-flattened map presented as an imported composition
  (`AE-COLLISION-06`, `AE-AC-11`).
- The build gate becomes a CI obligation. Without `ai-engine check-capabilities`
  in the pipeline, a dynamic composition is protected only by the best-effort
  static gate.
- Publishing a fourth package adds release, versioning, and compatibility work,
  even though it carries no runtime contract.
- Effective IDs become the only public identity (`AE-COMP-06`). Default IDs and
  provenance never reach `ExecutionContext`, business inputs, outputs, or
  events, so observability and access rules see exactly what they see today.
- Diagnostics are payload-free by construction, so a composition failure can be
  logged in full without leaking business data or credentials.
- The composition root becomes the single place where every imported capability,
  its source, and its effective ID are visible for review.
