# ADR 0030: Project entry points in devtools emulation

- Status: Accepted
- Date: 2026-08-13

## Context

ADR 0028 runs the CLI and MCP stdio emulations in a devtools-owned child
process that imports the built engine module and calls the published adapter.
That child is a composition root: it decides the principal the adapter starts
with, and it decides it from the identity selected in the interface.

The engine's own entry point is also a composition root, and it decides
differently. The starter generated by `create-invokta-engine` supplies
`principal: null` to both `runCli` and `serveMcpStdio` — no authentication at
all. Every example in this repository supplies a fixed `localPrincipal`
carrying domain attributes; `examples/composed-engine` supplies
`local:operations-analyst` with the permissions its capabilities check.

So the same capability, with the same arguments, through the same adapter,
answers differently depending on which root ran it:

```text
node dist/cli.js run community.search-knowledge-base --input '{"query":"refund"}'
  → the articles

the devtools CLI emulation, acting as the development identity local-dev
  → FORBIDDEN
```

The divergence runs both ways. Against a generated starter, whose root passes
no principal, an emulation acting as a development identity is more permissive
than the real command; against an example, whose root passes a rich principal,
it is less permissive. Neither is visible in the interface: the identity
control is presented identically for every adapter, as though it always
described what runs.

## Decision

The CLI and MCP stdio emulations may run the engine's own built entry point
instead of the devtools child. The interface presents the choice next to the
identity, and the developer names the entry point explicitly; the devtools
continues to discover nothing.

- The **devtools entry point** remains the default and is unchanged. The
  devtools is the composition root, the selected identity is the acting
  principal, and an `access` rule can be exercised as different actors.
- The **project entry point** is a path inside the project directory that the
  devtools spawns as it is: `node <entry> run <capability> --input <json>` for
  the CLI, and `node <entry>` spoken to over stdio for MCP. The engine's own
  composition root then supplies the principal, including no principal at all,
  and the identity selection does not apply. The interface disables it and
  says why.

A direct call has no project entry point. A generated `src/direct.ts` is a
demonstration script bound to one capability and one argument shape, not an
adapter with an invocation contract, so the direct emulation stays on the
devtools child.

The path is resolved against the directory `serve` runs in and must remain
inside it. It is spawned without a shell, as an argument to the same Node
executable that runs the dev server, and it receives the dev server's
environment without the devtools principal variable — the entry point's own
root is the only thing that decides identity. Nothing is discovered: an
absent selection means the devtools entry point, and a path that does not
exist fails as the spawned process reports it.

This extends ADR 0028 and changes none of its prohibitions. The devtools still
spawns only per-invocation adapter children and its engine host, still keeps no
process alive between invocations, and still adds no execution path: a project
entry point is the developer's own published adapter, reached through
`engine.invoke`.

## Consequences

- The Playground can show what the shipped command actually does, next to what
  the same capability does as another actor.
- A capability that an `access` rule rejects can be attributed to the rule or
  to the root that supplied the principal, instead of to either by guess.
- The reproduction command for a project entry point is the command the
  developer would type, verbatim.
- A project entry point that serves a different engine than the loaded module
  fails on an unknown capability; the devtools reports that rather than
  reconciling two catalogs.
- Extending this to a direct entry point, to an entry point outside the project
  directory, or to arguments beyond the invocation itself requires another
  architectural decision.
