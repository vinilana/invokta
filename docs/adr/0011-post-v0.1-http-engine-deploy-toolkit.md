# ADR 0011: Post-v0.1 HTTP engine deploy toolkit

- Status: Accepted
- Date: 2026-07-28

## Context

An engine that exposes MCP Streamable HTTP through `serveMcpHttp` is already a
complete stateless server, but nothing in the repository turns it into something
a team can run in a shared environment. Every author hand-writes the HTTP
composition root, invents environment-variable names for the bind host, port,
and allowlists, writes a container build from scratch, and has no standard way
to verify that a deployed endpoint is serving MCP. The same gap exists one level
down: composition roots read configuration from `process.env`, and every author
either exports variables by hand or adds an ad-hoc `dotenv` dependency with its
own precedence and parsing quirks.

None of the existing packages owns this responsibility. `@ai-engine/core` owns
capability contracts and execution, `@ai-engine/cli` and `@ai-engine/mcp` are
adapters over the single `engine.invoke` path, `@ai-engine/tooling` (ADR 0009)
is a development-time composition build gate, and `@ai-engine/installer`
(ADR 0010) configures MCP clients on an end user's machine. Generating container
build contexts and probing a public endpoint is none of those things.

Two draft specifications describe the resulting behavior:
`docs/specs/http-engine-build-and-deploy.md` defines the toolkit and its
`init`, `package`, and `probe` commands, and
`docs/specs/engine-env-file-loading.md` defines the environment-file convention
that the same toolkit scaffolds. Both defer a set of open decisions to an
authorizing ADR, and both are blocked without a package-boundary decision. This
ADR records that decision and its cost, not the requirement detail.

## Decision

The repository will add `packages/deploy`, published as `@ai-engine/deploy`,
after v0.1. It will be a native ESM, development-time application providing the
non-interactive `ai-engine-deploy` executable and declaring the repository
runtime floor of Node.js `>=22.20.0`.

The toolkit owns only:

- loading and validating the closed `ai-engine.deploy.json` deployment manifest;
- scaffolding a production-shaped HTTP composition root, its fail-closed
  authentication hook, the environment-file loader, and `.env.example`;
- generating a deterministic, reviewable deployment package: `Dockerfile`,
  `.dockerignore`, `deploy/healthcheck.mjs`, and `deploy/DEPLOYMENT.md`; and
- one bounded MCP liveness or readiness probe over an existing `/mcp` endpoint.

The detailed observable behavior, manifest schema, generated file set, probe
semantics, errors, limits, acceptance criteria, and delivery slices remain
governed by the two specifications above. This ADR authorizes the package and
its architectural boundary; it does not widen either specification.

### ADR 0004 is amended with a sixth published package

ADR 0004 is amended, not superseded. Its three v0.1 framework runtime packages
retain their names, responsibilities, ESM-only publication, and dependency
rules:

| Path | Published name | Responsibility |
| --- | --- | --- |
| `packages/core` | `@ai-engine/core` | Capability contracts and execution runtime |
| `packages/cli` | `@ai-engine/cli` | Capability command-line adapter |
| `packages/mcp` | `@ai-engine/mcp` | Model Context Protocol adapter |

ADR 0009 remains the authority for `@ai-engine/tooling` and ADR 0010 for
`@ai-engine/installer`. Once the toolkit ships, the project publishes six
packages while still having exactly three framework runtime packages. The v0.1
package count remains a historical limit of that release and is not
retroactively changed.

`@ai-engine/deploy` is the sixth published package and a standalone
development-time generator. No runtime, tooling, or installer package may depend
on it, and it MUST NOT depend on `@ai-engine/core`, `@ai-engine/cli`,
`@ai-engine/mcp`, `@ai-engine/tooling`, or `@ai-engine/installer`. It MUST use
only Node built-ins and declare no runtime dependency. Generated user code
imports `@ai-engine/mcp`; the toolkit itself never does, so the dependency
appears in the author's project and never in the toolkit's own graph.

### Generating text does not create an execution path

ADRs 0001, 0003, 0005, and 0007 remain in force and are not amended. The
toolkit validates and writes text. It never imports an `Engine`, calls
`engine.invoke`, executes a capability, or starts an adapter, and it is absent
from the invocation call graph.

- No command spawns a process, executes a shell, or runs a package manager,
  compiler, or container tool. The install commands the toolkit detects appear
  only as text inside a generated `Dockerfile`.
- `init` and `package` perform zero network operations; `probe` performs exactly
  one HTTP request per invocation, with no retry, redirect, or connection reuse.
- Generated code uses only the public `serveMcpHttp` API and its documented
  options. The scaffold adds no session, resumption, sticky routing, or
  in-adapter TLS, and the stateless HTTP profile of ADR 0007 is taken as given.
- The environment-file loader runs in the composition root, before an engine
  exists. Reading a file and mutating `process.env` are I/O concerns owned by
  the application composition root, exactly where ADR 0001 places them.

The toolkit's stable error codes and exit codes are toolkit contracts, and the
loader's startup failures are composition-root contracts. Neither extends the
seven-code `EngineError` taxonomy fixed by ADR 0003 nor the mappings owned by
`@ai-engine/cli`.

### The toolkit, the build gate, and the installer remain separate

ADRs 0009 and 0010 remain in force and are not superseded:

- `@ai-engine/tooling` is a development-time build gate, depends on the core's
  public composition API, and provides `ai-engine check-capabilities`;
- `@ai-engine/installer` is an end-user configuration application, has no
  framework-package dependency, and provides `ai-engine-installer`;
- `@ai-engine/deploy` is a development-time generator, has no framework-package
  dependency, and provides `ai-engine-deploy`; and
- no two of them may import each other, share a launcher, or acquire the
  other's responsibilities.

A deployed endpoint that follows the specification satisfies the installer's
`streamable-http` URL constraints, so its public URL can later appear in an
installer registry entry. That relationship is documentation, not a dependency:
automatic registration of a deployed endpoint remains outside this decision, as
does a unified `ai-engine` launcher.

### The open specification decisions are resolved as drafted

Both specifications defer decisions to this ADR. Each is resolved by adopting
the drafted preference:

- **A standalone package, not a tooling extension.** Container conventions and
  probe network access have a different release cadence and risk profile than
  the composition build gate, mirroring the reasoning that separated the
  installer. Tooling keeps its single build-gate authority.
- **Container-stage install from the lockfile, not a bundler.** The generated
  `Dockerfile` reinstalls from the project's own lockfile with the detected
  frozen-lockfile command. No JavaScript bundler is introduced.
- **Scaffolded source is user-owned from the first write.** `init` never
  overwrites an existing file, reports an existing target as skipped, and the
  toolkit performs no drift tracking over `src/`. Only the marked files of the
  deployment package are regenerated.
- **A 401 Bearer challenge is liveness.** `probe --expect alive` accepts an
  HTTP 401 carrying a `Bearer` challenge as healthy, so liveness never requires
  the probe to hold a credential. No health or metrics route is added to
  `@ai-engine/mcp`; liveness is observed from outside the existing `/mcp`
  boundary.
- **The environment loader ships as generated source.** The loader is
  user-owned application code emitted by `init`, parsing with Node's built-in
  `util.parseEnv`. No `@ai-engine/env` package, no runtime dependency, and no
  `dotenv` is introduced anywhere.
- **Environment key validation fails closed.** A key the loader would apply and
  that does not match the documented name pattern aborts startup naming only
  that key. Keys are never silently skipped, so a typo surfaces as an error
  rather than as a mysteriously absent variable.
- **No profile layering in the first release.** `.env.local`, per-mode files,
  and merge chains are deferred. The contract is exactly one environment file
  per process, and any later layering requires its own precedence
  specification.
- **No production guard inside the loader.** A production image contains no
  environment file, because `.dockerignore` excludes every `.env*` file from the
  build context. The loader adds no `NODE_ENV` check, which would be a
  behavioral trap in the many environments that do not set it.

The environment contract these decisions imply — the `AI_ENGINE_HTTP_*`
variables and `AI_ENGINE_ENV_FILE` — becomes a public convention of generated
application code once released. Renaming a variable is breaking for every
deployed engine and requires a documented migration.

### Delivery follows ADR 0008

Implementation MUST follow the executable delivery slices, acceptance criteria,
and RED/GREEN/REFACTOR workflow of both specifications. Each slice ends in its
own validated, cohesive commit.

This ADR and its index entry are a documentation-only architectural decision and
change no executable behavior. The RED step is therefore not applicable to this
slice under ADR 0008. All subsequent executable toolkit slices require failing
evidence before implementation.

## Alternatives considered and rejected

- **Add `deploy` subcommands to `@ai-engine/tooling`.** Rejected: it would widen
  a dev-only build gate that already depends on the core into a generator with
  container conventions and outbound network access, coupling two unrelated
  release cadences and risk profiles.
- **Add deployment commands to `@ai-engine/cli`.** Rejected: that adapter's
  responsibility is selecting and executing capabilities through
  `engine.invoke`. Generating infrastructure text is not capability execution.
- **Add a health or readiness route to `@ai-engine/mcp`.** Rejected: it would
  add a second HTTP surface to a runtime package for a development-time
  convenience, and the existing `/mcp` boundary already proves liveness through
  its authentication challenge.
- **Bundle the engine with a JavaScript bundler.** Rejected: it would shrink
  images at the cost of a heavy dependency, broken native modules, and output no
  reviewer can read.
- **Publish an `@ai-engine/env` runtime helper.** Rejected: it would add a
  published package and a runtime dependency for something `util.parseEnv`
  already covers at the pinned Node.js floor, and it would place file reading
  and `process.env` mutation inside a framework package.
- **Generate provider manifests or run the container build.** Rejected: the
  output is a conventional build context that any OCI builder consumes.
  Executing builders, deploying to a platform, and emitting Compose, Kubernetes,
  or Terraform manifests remain outside this decision.
- **Track and rewrite scaffolded source.** Rejected: drift tracking over
  `src/` would make the toolkit a co-owner of application code and turn a
  toolkit upgrade into an unreviewed source change.

## Consequences

- Engine authors gain a path from a working engine to a reviewable container
  build context with two commands, plus one probe usable in CI and as a
  container health check.
- The repository and release process gain a sixth published package with its own
  compatibility, dependency, security, and package-smoke obligations, even
  though it carries no runtime contract.
- The environment contract and the manifest become public surfaces. Because the
  manifest schema is closed and `schemaVersion` is exact, adding even an
  optional field is a schema change requiring a release decision.
- Generated files are committed artifacts. The marker policy is therefore a
  correctness requirement: an unmarked file is never overwritten, and
  regeneration of an unchanged file performs no write.
- Secret hygiene is a release requirement rather than optional hardening.
  Credentials enter only through an environment variable name, and diagnostics
  carry paths, JSON pointers, and HTTP statuses but never values, header
  contents, response bodies, or cause chains.
- Deployment topology becomes an operator obligation the generated
  documentation must state: a TLS-terminating edge in front of the engine, the
  original public `Host` forwarded, and the allowlist naming every public host.
- The framework keeps three runtime packages, the seven-code `EngineError`
  taxonomy, and one capability execution path. Existing v0.1, composition, and
  installer consumers require no migration.
