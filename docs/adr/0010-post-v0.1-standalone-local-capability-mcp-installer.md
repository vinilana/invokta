# ADR 0010: Post-v0.1 standalone local capability MCP installer

- Status: Accepted
- Date: 2026-07-28

## Context

Action Engine users need an end-user interface that can detect supported local AI
harnesses and configure an engine's MCP server in each harness's standard user
configuration. The operation is not capability execution: it validates a bundled
catalog of MCP descriptors, inspects local installation evidence, and applies an
explicitly confirmed configuration change.

None of the existing packages owns this responsibility. `@invokta/core` owns
capability contracts and execution, `@invokta/cli` invokes capabilities through
the core, and `@invokta/mcp` exposes capabilities to MCP clients. ADR 0009
added `@invokta/tooling` for a development-time composition build gate, not for
interactive end-user configuration or mutation of third-party application files.

Placing the installer inside one of those packages would mix dependencies,
authority, and release concerns. It would also blur the distinction between
configuring an MCP client and executing a capability. A package-boundary decision
is therefore required before implementing
`docs/specs/local-capability-mcp-installer.md`.

## Decision

The repository will add `packages/installer`, published as
`@invokta/installer`, after v0.1. It will be a native ESM end-user application
with the `invokta-installer` executable and the repository runtime floor of
Node.js `>=22.20.0`.

The installer owns only:

- validation and loading of the immutable local capability registry shipped in
  its package;
- finite, explicit detection of supported harness surfaces;
- harness-specific user-configuration adapters and safe, format-preserving MCP
  entry mutation;
- installer ownership state, preflight, locking, rollback, and diagnostics; and
- the interactive terminal experience specified for `@clack/prompts`.

The detailed observable behavior, supported targets, registry and state schemas,
errors, limits, acceptance criteria, and delivery slices remain governed by
`docs/specs/local-capability-mcp-installer.md`. This ADR authorizes the package
and its architectural boundary; it does not widen that specification.

### ADR 0004 is amended with one isolated post-v0.1 package

ADR 0004 is amended, not superseded. Its three v0.1 framework runtime packages
retain their names, responsibilities, ESM-only publication, and dependency
rules:

| Path | Published name | Responsibility |
| --- | --- | --- |
| `packages/core` | `@invokta/core` | Capability contracts and execution runtime |
| `packages/cli` | `@invokta/cli` | Capability command-line adapter |
| `packages/mcp` | `@invokta/mcp` | Model Context Protocol adapter |

ADR 0009 remains the authority for the fourth published package,
`@invokta/tooling`, and its development-only build-gate role. Once the
installer ships, the project therefore publishes five packages while still
having exactly three framework runtime packages. The v0.1 package count remains
a historical limit of that release and is not retroactively changed.

`@invokta/installer` is the fifth published package and a standalone end-user
configuration application. It is neither a framework runtime package nor
development-only tooling. No existing runtime or tooling package may depend on
it, and it MUST NOT depend on `@invokta/core`, `@invokta/cli`,
`@invokta/mcp`, or `@invokta/tooling`.

The installer MUST depend directly on `@clack/prompts` for its production
interactive experience. It MAY depend on Node built-ins and focused
format-preserving parsing or patching libraries. Those dependencies and their
types MUST remain inside the installer boundary. Clack types and cancellation
symbols MUST NOT become a public contract. No public programmatic mutation API
is authorized; the executable and its documented exit behavior are the public
surface.

### The local registry is configuration data, not a plugin system

ADR 0001 remains in force and is not amended. The installer's registry is one
versioned, read-only JSON document bundled with the package. Its records describe
MCP launch or connection configuration; they are not runtime capability modules,
ESM exports, package-resolution instructions, or registrations in the core.

The installer performs no remote discovery, package loading, reflection, hot
loading, dependency injection, lifecycle management, or mutable registration in
an engine. It does not scan for unknown harnesses or infer unsupported
configuration formats. Adding registry entries or adapters requires repository
review and a package release under the installer specification.

Although a configured harness may later launch a registry-declared command or
connect to an endpoint, the installer itself MUST NOT execute registry commands,
harness binaries, package managers, shells, engines, or capability handlers, and
MUST NOT open an MCP or network connection.

### Configuring MCP does not create an execution path

ADRs 0003 and 0005 remain in force and are not amended. The installer never
imports an `Engine`, calls `engine.invoke`, or starts an adapter. It only writes a
supported MCP client configuration after preflight and explicit user
confirmation.

When that harness later calls an Action Engine MCP server, execution still enters
through `@invokta/mcp` and the single `engine.invoke` pipeline. The installer
is absent from the invocation call graph. Its stable error codes and exit codes
are installer contracts, not additions to `EngineError` or mappings owned by
`@invokta/cli`.

### The installer and development tooling remain separate

ADR 0009 remains in force and is not superseded:

- `@invokta/tooling` is a development-time build gate, imports the core's
  public composition API, and provides the `invokta check-capabilities`
  command;
- `@invokta/installer` is an end-user configuration application, has no
  framework-package dependency, and provides only `invokta-installer`; and
- neither package may import or invoke the other, share a launcher, or acquire
  the other's responsibilities.

A unified `invokta` launcher, capability composition or discovery in the
installer, and installation features in the tooling package remain outside this
decision.

### Delivery follows ADR 0008

Implementation MUST follow the executable delivery slices, acceptance criteria,
and RED/GREEN/REFACTOR workflow in the installer specification. Each slice ends
in its own validated, cohesive commit.

This ADR and its index entry are a documentation-only architectural decision and
change no executable behavior. The RED step is therefore not applicable to this
slice under ADR 0008. All subsequent executable installer slices require failing
evidence before implementation.

## Alternatives considered and rejected

- **Add installation commands to `@invokta/tooling`.** Rejected: tooling is a
  development-only build gate with a core dependency, while the installer is an
  end-user application with authority to inspect and mutate harness user
  configuration. Combining them would couple unrelated dependencies and release
  concerns.
- **Add installation commands to `@invokta/cli`.** Rejected: that adapter's
  responsibility is selecting and executing capabilities through `engine.invoke`.
  Local harness discovery, ownership state, and third-party configuration writes
  are not capability execution.
- **Add the registry or mutation logic to `@invokta/core` or
  `@invokta/mcp`.** Rejected: it would introduce filesystem, terminal, harness,
  and configuration-format concerns into framework runtime packages and reverse
  the dependency direction established by ADRs 0001 and 0004.
- **Use the `invokta` tooling executable as a shared launcher.** Rejected for
  the first release: it would make development tooling an end-user dependency
  and obscure which package owns configuration writes and exit behavior.
- **Discover and install packages from a remote marketplace.** Rejected: the
  first release installs configuration only, has no network operations, and
  requires a reviewed bundled registry.

## Consequences

- Users gain one interactive executable for supported MCP client configuration
  without changing engine capability contracts or execution behavior.
- The repository and release process gain a fifth published package with its own
  compatibility, dependency, security, and package-smoke obligations.
- Harness configuration formats are an explicit compatibility boundary. The
  installer must fail closed when current fixtures no longer prove a safe write.
- The package acquires local user-configuration authority, so ownership checks,
  secret-free diagnostics, explicit confirmation, atomic writes, bounded locks,
  and rollback are release requirements rather than optional hardening.
- `@clack/prompts` becomes a reviewed production dependency of the installer but
  remains isolated from all public and framework contracts.
- The framework keeps three runtime packages, the seven-code `EngineError`
  taxonomy, and one capability execution path. Existing v0.1 and composition
  consumers require no migration.
