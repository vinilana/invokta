# Interactive engine creator profiles specification

Status: Implemented by ADR 0018

Contract review verdict: **APPROVED**

## Summary

`create-invokta-engine` will become interactive by default when attached to a
terminal. It will collect or confirm the project directory, ask whether to
generate the complete scaffold or one adapter-specific scaffold, show the
resolved plan, and require a final confirmation before writing anything.

The supported scaffold profiles are:

- `complete`: direct invocation, CLI, MCP local over stdio, and MCP HTTP;
- `mcp-stdio`: direct invocation and MCP local over stdio;
- `mcp-http`: direct invocation and MCP HTTP; and
- `cli`: direct invocation and CLI.

“MCP local” is the interactive label. `mcp-stdio` is the stable command-line
and programmatic identifier because it names the actual transport.

Non-terminal automation remains supported. An explicit positional target is
treated as the location decision, the omitted profile defaults to `complete`,
and no prompt is attempted. `--yes` gives terminal automation an explicit way
to bypass all prompts.

The durable decision is recorded in ADR 0018. Normative behavior lives in the
architecture, package documentation, and acceptance tests linked by the
validation record.

## Problem

The creator currently requires a project directory, is always non-interactive,
and emits one fixed scaffold containing direct, CLI, and MCP stdio entry points.
Authors must remove unwanted adapters manually, while MCP HTTP must be added in
a separate `@invokta/deploy init` step.

The desired initializer should guide a human through the two decisions that
materially affect the generated project:

1. where the project will be initialized; and
2. which adapter surface the starter should contain.

The change must not make CI hang, weaken the target safety boundary, create a
second capability execution path, or duplicate the MCP HTTP templates currently
owned by `@invokta/deploy`.

## Goals

- Make terminal use interactive by default.
- Allow the project directory to be supplied by a prompt or positional
  argument.
- Require a final confirmation that names both the selected profile and the
  normalized project location.
- Generate one of four deterministic profiles: `complete`, `mcp-stdio`,
  `mcp-http`, or `cli`.
- Keep `src/direct.ts`, the capability, engine, tests, project instructions,
  and development skill in every profile.
- Include only the runtime and development dependencies needed by the selected
  profile.
- Preserve non-terminal automation and provide an explicit prompt bypass for
  terminal automation.
- Keep every generated adapter on the single `engine.invoke` path.
- Reuse the MCP HTTP scaffold authority from `@invokta/deploy` without invoking
  another CLI or introducing partial writes.

## Non-goals

- Selecting more than one individual adapter except through `complete`.
- A custom template language, remote template catalog, or plugin system.
- Selecting capabilities, model providers, databases, identity providers, or
  deployment platforms.
- Generating A2A while its adapter specification remains proposed.
- Implementing an HTTP authentication provider or enabling insecure HTTP by
  default.
- Prompting for package-manager choice or dependency installation. Existing
  flags and package-manager inference remain authoritative.
- Git initialization, repository creation, package publication, or deployment.
- Updating projects previously generated by the creator.
- Adding an interactive dependency when a bounded implementation using Node
  facilities is sufficient.

## Command contract

The command surface becomes:

```text
create-invokta-engine [project-directory]
  [--profile complete|mcp-stdio|mcp-http|cli]
  [--package-manager npm|pnpm|yarn]
  [--no-install]
  [--yes]
create-invokta-engine --help
create-invokta-engine --version
```

Arguments may appear in any order except that option values immediately follow
their option. There may be at most one positional project directory. Duplicate
options, missing values, unknown options, unknown profile identifiers, extra
positionals, and combining `--help` or `--version` with anything else are
invalid usage.

`--yes` means “accept the defaults and skip every prompt.” It does not select a
package manager and does not override `--no-install`. `--yes` requires an
explicit positional project directory; an omitted `--profile` still means
`complete`.

## Interaction modes

The creator determines interaction mode exactly once after parsing arguments.
It is interactive only when all of these are true:

- `--yes` is absent;
- standard input is a TTY; and
- standard error is a TTY.

Standard error is the prompt channel so standard output remains reserved for
help, version, cancellation, and the final success summary.

### Interactive mode

Interactive mode follows this fixed order:

1. Ask for the project directory when the positional argument is absent.
2. Ask for the scaffold profile when `--profile` is absent.
3. Select the package manager using the existing explicit, user-agent, then npm
   precedence.
4. Validate the target syntax and preflight its filesystem location without
   writing.
5. Build the complete deterministic scaffold plan.
6. Display and ask for final confirmation of profile, relative location, and
   installation behavior.
7. Only after an affirmative answer, create the scaffold and optionally install
   dependencies.

Supplying a positional project directory skips only the directory question. A
supplied profile skips only the profile question. Unless `--yes` is present,
the final confirmation is never skipped in interactive mode.

### Non-interactive mode

When either required stream is not a TTY, the creator MUST NOT read standard
input or render a prompt.

- An explicit positional project directory is required.
- An omitted profile defaults to `complete`.
- The explicit project directory counts as the location decision, so no final
  confirmation is attempted.
- Existing package-manager inference and installation behavior are unchanged.
- An omitted project directory fails with `INTERACTIVE_REQUIRED`, exit code `2`,
  before loading templates, touching the filesystem, or starting a child
  process.

This preserves existing non-terminal calls such as
`create-invokta-engine my-engine --no-install`, while terminal automation can
use `--yes` to avoid a prompt even when a pseudo-TTY is present.

## Prompt contract

All prompt content is English, has no ANSI color requirement, and is rendered
deterministically. The logical transcript is:

```text
Project directory (my-invokta-engine):
Scaffold profile:
  1. Complete (CLI + MCP local + MCP HTTP)
  2. MCP local (stdio)
  3. MCP HTTP
  4. CLI
Choose a profile (1):
Create the complete scaffold in "my-engine" and install dependencies with npm? (y/N)
```

The exact final question changes only its profile label, normalized relative
target, package manager, and the phrase `without installing dependencies` when
`--no-install` is present. It MUST NOT show an absolute path.

Prompt defaults and accepted input are:

| Question | Empty answer | Accepted non-empty answer |
| --- | --- | --- |
| Project directory | `my-invokta-engine` | Any target accepted by the existing creator target contract |
| Profile | `complete` | `1`, `2`, `3`, or `4` |
| Confirmation | No | Case-insensitive `y`, `yes`, `n`, or `no`, after trimming |

Each prompted directory answer is syntax-validated before the creator advances
to profile selection; an invalid answer consumes one attempt. Once an answer is
syntactically valid, an unsafe, non-directory, or non-empty filesystem target
fails with the existing target code instead of prompting for a different path.

Each answer is decoded as strict UTF-8 and limited to 4,096 encoded bytes,
including the line terminator. The first byte beyond the limit, malformed
UTF-8, or three invalid answers to the same question fails with
`PROMPT_INVALID`, exit code `2`. The creator retains at most one current answer
and one fixed-size prompt buffer.

End-of-file, terminal interruption, or a prompt reader or writer failure before
confirmation fails with `PROMPT_ABORTED`, exit code `1`. No scaffold write or
package-manager process may have started at that point.

A negative final confirmation is a normal cancellation. It writes exactly
`Creation cancelled. No files were created.\n` to standard output, writes no
diagnostic, returns exit code `0`, and performs no filesystem mutation, child
process execution, or network operation.

Prompt validation diagnostics never echo a rejected answer. The accepted,
normalized relative target may appear in the confirmation and success summary.
The confirmation escapes Unicode control, format, line-separator, and
paragraph-separator characters instead of emitting terminal-active text.

## Profile model

The implementation uses this closed profile type:

```ts
export type EngineStarterProfile =
  | "complete"
  | "mcp-stdio"
  | "mcp-http"
  | "cli";
```

The package remains binary-only, so this type is an implementation and test
contract rather than a new package export. The selected profile is captured
once before the scaffold plan is built and cannot change during creation.

### Common scaffold

Every profile contains these 13 entries in lexicographic path order:

```text
.agents/skills/develop-invokta-project/SKILL.md
.agents/skills/develop-invokta-project/agents/openai.yaml
.gitignore
AGENTS.md
CLAUDE.md -> AGENTS.md
README.md
package.json
src/capabilities/create-welcome-message.ts
src/direct.ts
src/engine.ts
test/engine.test.ts
tsconfig.json
tsconfig.test.json
```

The common `package.json` contains `@invokta/core`, `zod`, the existing build,
typecheck, test, check, and direct scripts, and the existing development tools.
The capability, engine, direct entry point, and engine test remain byte-for-byte
equivalent for the same project name, Invokta version, and package manager.

### Adapter additions

| Profile feature | Added entries | Added project dependencies and scripts |
| --- | --- | --- |
| CLI | `src/cli.ts` | `@invokta/cli`; `cli` |
| MCP local | `invokta.mcp.json`, `src/mcp-stdio.ts` | `@invokta/mcp`, development dependency `@invokta/installer`; `mcp:stdio`, build-first `mcp:install`, and build-free `mcp:uninstall` |
| MCP HTTP | `.env.example`, `invokta.deploy.json`, `src/env.ts`, `src/http-auth.ts`, `src/mcp-http.ts` | `@invokta/mcp`, development dependency `@invokta/deploy`; `mcp:http`, `deploy:package`, and `deploy:probe` |

Profile composition is exact:

| Profile | Common | CLI | MCP local | MCP HTTP | Total entries |
| --- | ---: | ---: | ---: | ---: | ---: |
| `complete` | Yes | Yes | Yes | Yes | 21 |
| `mcp-stdio` | Yes | No | Yes | No | 15 |
| `mcp-http` | Yes | No | No | Yes | 18 |
| `cli` | Yes | Yes | No | No | 14 |

Dependencies are set unions and occur once. Generated Invokta dependency
versions exactly match the creator version. A profile MUST NOT mention, import,
document, script, or depend on an adapter it does not include.

For profiles containing MCP local, the scripts remain exactly:

```json
{
  "mcp:stdio": "node dist/mcp-stdio.js",
  "mcp:install": "tsc -p tsconfig.json --pretty false && invokta-installer install --engine .",
  "mcp:uninstall": "invokta-installer remove --engine ."
}
```

For profiles containing MCP HTTP, the scripts are exactly:

```json
{
  "mcp:http": "node dist/mcp-http.js",
  "deploy:package": "invokta-deploy package",
  "deploy:probe": "invokta-deploy probe"
}
```

The HTTP `.gitignore` variant ignores `.env` and `.env.*` while retaining
`!.env.example`. The HTTP authentication module is fail-closed and contains no
development authentication bypass. Generated HTTP code continues to implement
the environment, shutdown, Host allowlist, and secret-handling contract of ADR
0011.

`README.md`, `AGENTS.md`, and the generated development skill are rendered from
the selected profile. Their execution-channel instructions list exactly the
generated direct and adapter entry points. HTTP profiles explain that the auth
hook must be implemented before the server can start. MCP local profiles
document both install and uninstall. No generated text says a missing adapter is
available.

## MCP HTTP template ownership

`@invokta/deploy` remains the single owner of MCP HTTP scaffold bytes. It will
expose a pure, side-effect-free subpath API:

```ts
import {
  createMcpHttpScaffoldFiles,
  starterDeployManifest,
} from "@invokta/deploy/scaffold";
```

The planner returns immutable, project-relative UTF-8 text entries in
lexicographic order. It performs no filesystem access, process execution,
network access, engine import, or capability invocation.

The creator depends on the matching exact `@invokta/deploy` version and merges
the planner's five entries with its own entries before creating a directory or
file. It MUST NOT run `invokta-deploy init`, import an internal source path,
copy the five templates, or write the base scaffold before the HTTP plan is
complete.

This preserves one template authority and the creator's existing all-or-rollback
pre-install transaction. `invokta-deploy init` remains available for adding HTTP
to an existing project.

## Filesystem and installation semantics

All existing target rules remain unchanged:

- targets are relative to the working directory;
- `.` is accepted only for an otherwise valid empty working directory;
- absolute paths, parent segments, unsafe symbolic links, non-directories, and
  non-empty targets are rejected;
- target and project-name limits remain unchanged;
- writes and symbolic links use exclusive creation and never overwrite;
- generated text is deterministic UTF-8 with LF endings and one trailing
  newline;
- a pre-install failure rolls back only entries and directories created by the
  invocation; and
- an install failure preserves the complete generated scaffold.

Target preflight before confirmation is advisory against races. The creator
MUST revalidate through the existing no-follow and exclusive-write boundary
after confirmation. A path becoming unsafe or non-empty between those checks
fails with the existing target or conflict error and never overwrites the new
entry.

Unless `--no-install` is present, exactly one existing shell-free package-manager
install runs after every selected scaffold entry has been created. Profile
selection, planning, and confirmation perform no network request and spawn no
process. The creator adds no retry or timeout to the foreground install.

Concurrent creation in one target remains unsupported. Exclusive creation
prevents either invocation from replacing the other's entry.

## Output and errors

Help, version, normal cancellation, and the final success summary use standard
output. Prompts and diagnostics use standard error. The install child continues
to inherit terminal streams. No output contains a stack, cause, environment
value, credential, rejected answer, or rejected path.

The success summary names the project and profile:

```text
Created my-engine with the complete scaffold.

Next step:
  npm run check
```

The existing installed and `--no-install` next-step variants remain, with only
the first line changed to include the profile label.

The error taxonomy adds three codes:

| Code | Exit | Stable message |
| --- | ---: | --- |
| `INTERACTIVE_REQUIRED` | `2` | `Interactive input is required when no project directory is provided.` |
| `PROMPT_INVALID` | `2` | `Interactive input is invalid.` |
| `PROMPT_ABORTED` | `1` | `Interactive project creation was interrupted.` |

Existing codes, messages, exit statuses, and sanitization remain unchanged.
Invalid command-line syntax continues to use the compact generic usage
diagnostic rather than exposing the rejected argument or profile value.

## Timeout, cancellation, concurrency, and idempotency

- Human think time has no creator-owned timeout. The prompt retains only a
  bounded current line and performs no work while waiting.
- EOF, prompt interruption, or prompt I/O failure before confirmation performs
  no writes and starts no install.
- A normal negative confirmation is idempotent and has no side effect.
- After confirmation, filesystem rollback and foreground install cancellation
  retain the existing ADR 0012 semantics.
- Repeating a successful creation against the same target fails as non-empty;
  the creator never treats a different profile as an in-place conversion.
- Only one prompt is active at a time. The creator adds no worker, queue,
  background task, retry, or concurrent write mechanism.

## Requirements

### AE-CREATE-PROFILE-01: Interactive default

Terminal execution without `--yes` MUST collect missing location and profile
answers and MUST request final confirmation before mutation.

### AE-CREATE-PROFILE-02: Automation

Non-terminal execution MUST never prompt. An explicit target MUST proceed with
the explicit profile or `complete` default. A missing target MUST fail
deterministically with `INTERACTIVE_REQUIRED`.

### AE-CREATE-PROFILE-03: Location confirmation

The final interactive confirmation MUST name the normalized relative target,
selected profile, and installation choice without exposing an absolute path.
Only an affirmative answer authorizes writes.

### AE-CREATE-PROFILE-04: Closed profile set

The creator MUST accept only `complete`, `mcp-stdio`, `mcp-http`, and `cli`, with
the exact composition and file counts defined here.

### AE-CREATE-PROFILE-05: Minimal generated dependencies

Each generated manifest MUST contain the union of common dependencies and only
the dependencies and scripts required by its selected adapters.

### AE-CREATE-PROFILE-06: Single execution path

Every generated direct or adapter entry point MUST use the shared engine and
MUST reach capability execution only through `engine.invoke` or an official
adapter that itself uses `engine.invoke`. No profile may duplicate a capability
handler.

### AE-CREATE-PROFILE-07: HTTP ownership and safety

MCP HTTP profiles MUST use the pure public scaffold planner owned by
`@invokta/deploy`, include its fail-closed auth and environment contracts, and
merge the full plan before any write.

### AE-CREATE-PROFILE-08: Prompt limits and failures

Prompt input, attempts, EOF, interruption, output failure, errors, exit statuses,
and secret-free diagnostics MUST follow the bounded contract above.

### AE-CREATE-PROFILE-09: Filesystem safety

All profiles MUST preserve target validation, no-follow inspection, exclusive
creation, deterministic bytes, rollback, and non-overwrite guarantees.

### AE-CREATE-PROFILE-10: Installation boundary

At most one package-manager install may run, only after affirmative or implicit
non-terminal authorization and a complete scaffold. `--no-install` MUST start no
child process or network activity.

### AE-CREATE-PROFILE-11: Profile-aware documentation

Generated README, instructions, development skill, commands, and manifests MUST
describe exactly the selected channels and MUST NOT advertise omitted adapters.

### AE-CREATE-PROFILE-12: Architectural decision

Before release, a new ADR MUST supersede ADR 0012's non-interactive and fixed
starter decisions, authorize profile-specific generated engines under the reuse
invariant, and amend ADR 0011 to expose its pure HTTP scaffold planner to the
creator without transferring template ownership.

## Compatibility and migration

This is a breaking behavioral change for terminal users:

- `create-invokta-engine my-engine` will now ask for a profile and confirmation
  when stdin and stderr are TTYs;
- terminal automation must add `--yes`;
- the default `complete` scaffold adds MCP HTTP files and `@invokta/deploy` to
  the previous direct, CLI, and MCP stdio starter; and
- success text and deterministic scaffold snapshots change.

Non-terminal invocations with an explicit target remain non-interactive and
continue to accept an omitted profile, which now resolves to `complete`.
Automation that requires a stable file set SHOULD pass both
`--profile <profile>` and `--yes` explicitly.

Existing generated projects are unaffected and receive no migration. A user
who wants another adapter after creation adds it manually; the creator never
re-enters or modifies a non-empty project.

The change must be released as an intentionally breaking creator release under
the repository's pre-1.0 versioning policy, not as an undocumented patch.
Release notes MUST include the old-to-new command mapping:

```text
create-invokta-engine my-engine --no-install
create-invokta-engine my-engine --profile complete --no-install --yes
```

## Architecture review

The package count and runtime adapter packages do not change. Profile selection
is development-time generation only and creates no capability execution path.
Every generated adapter continues to delegate to the same engine.

Three accepted boundaries require an explicit update:

1. ADR 0012 currently requires non-interactive creation and one fixed starter.
2. ADR 0011 currently gives `@invokta/deploy` sole HTTP scaffold ownership but
   does not expose its pure planner as a public subpath.
3. `AE-INV-04` and the release gates currently require every reference engine
   to demonstrate direct, CLI, and MCP reuse. Focused profiles demonstrate
   direct plus one selected adapter, while `complete` remains the conformance
   profile that proves all official adapters together.

The required ADR must state that focused scaffolds are valid bounded bootstrap
projects, while the `complete` profile remains the release conformance fixture.
It must not weaken the single-invoke invariant or claim an omitted adapter is
supported by a focused generated project.

Unspecified within this proposal: none. Terminal rendering libraries, cursor
movement, and visual styling are implementation details and may change without
changing the logical prompt transcript or accepted answers.

## Contract review verdict

**APPROVED**

ADR 0018 is accepted; RED/GREEN evidence covers every executable acceptance
surface; the deploy planner is public and independently validated; packed smoke
tests cover all four profiles and authenticated MCP HTTP; and compatibility
notes document terminal prompting, `--yes`, the new `complete` default, and
profile-specific dependencies.
