Invokta publishes four runtime packages, three optional runtime helpers,
and seven supporting packages. Each has one bounded responsibility.

## Runtime packages

| Package | Public role | Start here |
| --- | --- | --- |
| `@invokta/core` | Capability contracts, execution, composition, errors, and events | [Core reference](/reference/core/) |
| `@invokta/cli` | Local `list`, `describe`, `help`, and `run` with JSON or schema-derived flags over `engine.invoke` | [CLI reference](/reference/cli/) |
| `@invokta/mcp` | MCP tools over stdio and stateless Streamable HTTP | [MCP reference](/reference/mcp/) |
| `@invokta/http` | Plain HTTP JSON routes, OpenAPI 3.1 export, and a Node server entry point | [HTTP reference](/reference/http/) |

The core has no adapter or SDK dependency. CLI, MCP, and HTTP import only its
public API and never call capability handlers directly.

## Optional runtime helpers

| Package | Public role | Start here |
| --- | --- | --- |
| `@invokta/auth-jwt` | Verify one issuer's JWT bearer access tokens as the MCP HTTP or plain HTTP `authenticate` hook | [JWT bearer reference](/reference/auth-jwt/) |
| `@invokta/otel` | Record OpenTelemetry spans and invocation metrics from engine events as the `onEvent` hook | [OpenTelemetry reference](/reference/otel/) |
| `@invokta/gateway` | Serve several engines and MCP servers as one capability map with authentication helpers, first-match rules, per-caller visibility, and search-based discovery | [Gateway reference](/reference/gateway/) |

`@invokta/auth-jwt` depends only on `jose`, `@invokta/otel` only on core
types and the `@opentelemetry/api` peer, and `@invokta/gateway` only on the
core. No runtime package depends on a helper; a host-written authentication or
`onEvent` hook, or a host-composed engine, remains equally supported.
`@invokta/otel` observes events and never invokes a capability, and every
gateway call still enters through `engine.invoke`.

## Supporting packages

| Package | Public role | Start here |
| --- | --- | --- |
| `@invokta/tooling` | Validate a built, tracked capability composition and MCP catalog, and diff capability contracts, in development or CI | [Tooling reference](/reference/tooling/) |
| `@invokta/devtools` | Open the MCP and CLI workbenches, or serve a built engine with a web inspector, trace, and doctor diagnostics | [Devtools reference](/reference/devtools/) |
| `@invokta/installer` | Install and manage Action Engine MCP servers in supported local clients | [Installer reference](/reference/installer/) |
| `@invokta/deploy` | Scaffold/package HTTP deployment artifacts, probe health, and inspect OAuth discovery | [Deploy reference](/reference/deploy/) |
| `create-invokta-engine` | Create a standalone starter engine and install its dependencies | [Creator reference](/reference/create-invokta-engine/) |
| `create-invokta-capability` | Create a standalone atomic capability package | [Atomic creator reference](/reference/create-invokta-capability/) |
| `create-invokta-capability-library` | Create a standalone capability-library package | [Library creator reference](/reference/create-invokta-capability-library/) |

Supporting packages do not create another capability execution path. The
creators write projects, tooling imports a trusted composition module, the
installer updates client configuration without invoking an engine, and deploy
generates files or makes one probe request.

## Shared requirements

- Native ESM
- Node.js 22.20.0 or later
- Package-root imports only unless a package explicitly documents a subpath
- Runtime behavior remains on `engine.invoke`

Use the [error reference](/reference/errors/) for capability invocation errors.
Creator, tooling, installer, and deploy diagnostics have separate
application-specific contracts.
