---
title: Authenticate with a JWT bearer token
description: Verify an OIDC access token with @invokta/auth-jwt and map its claims to a Principal at the MCP HTTP boundary.
---

import { Aside, Steps } from '@astrojs/starlight/components';

Any identity provider that issues JWT access tokens and publishes a JWKS plugs
into Invokta the same way: the `serveMcpHttp` `authenticate` hook verifies the
token, maps a few verified claims to a `Principal`, and hands it to
`engine.invoke`. Nothing about the provider reaches a capability.

The optional [`@invokta/auth-jwt`](/reference/auth-jwt/) package is that hook.
This recipe configures it for a generic OIDC issuer; the provider-specific
recipes change only the issuer, the audience, the key-set location, and the
claim names.

## Build the integration

<Steps>

1. Install the authenticator

   ```sh
   yarn add @invokta/auth-jwt
   ```

   It depends only on `jose`. The engine and its capabilities do not import
   it; only the HTTP composition root does.

2. Configure the authentication policy

   ```ts
   export const defaultSignatureAlgorithms: ReadonlyArray<JwtSignatureAlgorithm> =
     Object.freeze(["RS256", "ES256"]);

   const authenticate = createJwtBearerAuthenticator({
     issuer,
     audience: requireValue("AUTH_JWT_AUDIENCE"),
     algorithms: readAlgorithms(),
     jwksUrl: resolveJwksUri(issuer, process.env.AUTH_JWT_JWKS_URI),
     ...(requiredScopes === undefined ? {} : { requiredScopes }),
   });
   ```

   Every check the security policy depends on is configured here: the exact
   issuer, the audience, an explicit signature algorithm allowlist, and the
   key-set URL. The token must also carry `sub` and `exp`. The authenticator
   rejects `none`, shared-secret `HS*` algorithms, and a plaintext key-set URL
   off loopback when it is created, so a misconfiguration fails at startup
   rather than on the first request.

3. Validate algorithm names from configuration

   ```ts
   function readAlgorithms(): ReadonlyArray<JwtSignatureAlgorithm> {
     const configured = readList("AUTH_JWT_ALGORITHMS");
     if (configured === undefined) return defaultSignatureAlgorithms;
     const algorithms = configured.filter(isJwtSignatureAlgorithm);
     if (algorithms.length !== configured.length) {
       throw new Error(
         "AUTH_JWT_ALGORITHMS may list only asymmetric JWS algorithms such as RS256 or ES256.",
       );
     }
     return algorithms;
   }
   ```

   `isJwtSignatureAlgorithm` narrows an environment string to the supported
   asymmetric algorithms, so the allowlist stays typed without a cast.

4. Resolve the key set at the composition root

   ```ts
   export function resolveJwksUri(issuer: string, override?: string): string {
     if (override !== undefined && override !== "") return override;
     return conventionalJwksUri(issuer);
   }
   ```

   `conventionalJwksUri` falls back to `<issuer>/.well-known/jwks.json` — a
   widespread convention, not a specification requirement. The authoritative
   location is the `jwks_uri` member of
   `<issuer>/.well-known/openid-configuration`; read it once and set
   `AUTH_JWT_JWKS_URI` when your provider hosts its key set elsewhere. The
   authenticator holds the URL to HTTPS, with loopback HTTP only for local
   development: a key set fetched over plaintext HTTP could be replaced by an
   on-path attacker, and a substituted key turns into accepted
   attacker-minted tokens.

   The remote key set is fetched on first use with a 5-second timeout, cached
   for 10 minutes, and refetched for an unknown key identifier at most once
   every 30 seconds.

5. Know what reaches the `Principal`

   ```ts
   {
     id: "user-42",
     attributes: {
       scopes: ["engine:invoke", "reports:read"],
       issuer: "https://identity.example.com",
       clientId: "reporting-cli",
     },
   }
   ```

   The default mapping is an allowlist. `sub` becomes `Principal.id`; the
   space-delimited `scope` claim, `iss`, and `client_id` become attributes an
   access rule can read. Every other claim — email, name, provider metadata,
   the raw token — stays out. Pass a `principal` mapper to choose other
   verified claims; it receives the claims, never the token, and returns
   `null` to reject the credential.

6. Separate an invalid credential from a broken check

   The authenticator resolves `null` for a missing, malformed, oversized,
   expired, not-yet-valid, wrongly issued, wrongly addressed,
   disallowed-algorithm, unknown-key, or bad-signature credential. The adapter
   answers 401 and never says which check failed.

   A key-set timeout, an unreachable or malformed key set, or a cancelled
   request means the check never happened, so the authenticator rejects with
   `JwtVerificationUnavailableError` instead. Its message is fixed and it has
   no cause, so no token, URL, or provider response can reach a log through
   it; the adapter answers a sanitized 500.

   A key set with two same-algorithm keys and no `kid` to choose between them
   is reported the same way. That is the issuer's key-publication problem,
   not evidence against the credential, and treating it as 401 would silently
   reject every legitimate token during a kid-less key rotation.

7. Wire the hook

   ```ts
   export async function startAuthJwtBearerMcpHttp(
     options: AuthJwtBearerMcpHttpOptions,
   ): Promise<McpHttpServerHandle> {
     return serveMcpHttp(engine, {
       ...(options.host === undefined ? {} : { host: options.host }),
       ...(options.port === undefined ? {} : { port: options.port }),
       auth: {
         mode: "required",
         authenticate: options.authenticate,
         ...(options.resourceMetadata === undefined
           ? {}
           : { resourceMetadata: options.resourceMetadata }),
         ...(options.challengeScopes === undefined
           ? {}
           : { challengeScopes: options.challengeScopes }),
       },
     });
   }
   ```

   The authenticator observes the request signal, so its work stops when the
   caller disconnects. Three outcomes, three HTTP results: a principal
   continues to `engine.invoke`, `null` becomes 401, and a rejection becomes a
   sanitized 500.

8. Require base scopes and name them in the challenge

   ```sh
   AUTH_JWT_REQUIRED_SCOPES=engine:invoke
   AUTH_JWT_RESOURCE=https://engine.example.com/mcp
   AUTH_JWT_CHALLENGE_SCOPES=engine:invoke
   ```

   With `requiredScopes`, a token that does not grant every listed scope
   resolves `null`. Because the hook can return only a principal or `null`,
   the caller receives 401 rather than an `insufficient_scope` 403, so list
   the same scopes in the challenge: an OAuth client reads them from the
   `WWW-Authenticate` header and requests them. Scopes that only some
   capabilities need belong in those capabilities' `access` rules.

9. Keep the capability free of identity plumbing

   ```ts
   export const whoami = defineCapability({
     title: "Who am I",
     description: "Return the verified identity of the current caller.",
     input,
     output,
     access: "authenticated",
     async run({ context }) {
       const { principal } = context;
       if (principal === null) {
         throw new EngineError({
           code: "UNAUTHENTICATED",
           message: "The request has no verified identity.",
         });
       }
       return {
         principalId: principal.id,
         attributes: { ...(principal.attributes ?? {}) },
       };
     },
   });
   ```

   `access: "authenticated"` closes the capability on every channel, and `run`
   reads `context.principal` only. Input cannot name, widen, or override an
   identity.

</Steps>

<Aside type="caution" title="Audience is not optional">
  A token that verifies against your issuer but was minted for a different
  resource must be rejected. Set `audience` to this engine's canonical `/mcp`
  URL; the authenticator requires it. Without that check, any service sharing
  the issuer could replay its tokens against your engine.
</Aside>

<Aside type="tip" title="Write your own hook when the helper does not fit">
  The helper verifies one issuer's signed JWTs. Opaque tokens that need
  introspection, several issuers, sender-constrained tokens, or a provider SDK
  such as `@clerk/backend` `verifyToken`, `firebase-admin` `verifyIdToken`, or
  `aws-jwt-verify` need a host-written hook. It still returns a `Principal` for
  a valid credential, `null` for an invalid one, and throws only when the
  check could not run; the rest of this recipe is unchanged.
</Aside>

## Run it

Build the repository, then start the engine against your provider:

```sh
yarn build
AUTH_JWT_ISSUER="https://your-tenant.example.com/" \
AUTH_JWT_AUDIENCE="http://127.0.0.1:3000/mcp" \
PORT=3000 \
node examples/auth-jwt-bearer-engine/dist/mcp-http.js
```

Call it with an access token your provider issued for that audience:

```sh
curl -s http://127.0.0.1:3000/mcp \
  -H "authorization: Bearer $ACCESS_TOKEN" \
  -H 'accept: application/json, text/event-stream' \
  -H 'content-type: application/json' \
  -d '{"jsonrpc":"2.0","id":"1","method":"tools/call","params":{"name":"identity_whoami","arguments":{}}}'
```

The same request without the header returns HTTP 401 with a `WWW-Authenticate:
Bearer` challenge, and `engine.invoke` is never reached. To make that challenge
carry a discovery pointer, follow
[Discover the Authorization Server](/recipes/auth/mcp-oauth-discovery/).

## Verify it

The example mints tokens from a key pair generated inside the test process and
passes the public half to the authenticator as a local `jwks`, so signature
verification is real and nothing leaves the machine:

```sh
yarn workspace @invokta/example-auth-jwt-bearer test
```

The suite covers the valid credential, the invalid classes this configuration
must reject (missing header, wrong scheme, malformed, expired, wrong issuer,
wrong audience, unknown key, bad signature, algorithm outside the allowlist,
missing subject, missing required scope), a key-set outage served by a loopback
endpoint, and the assertion that no token material appears in the produced
principal. Cancellation, the remote key-set cache, and every bearer parsing
rule are covered by the `@invokta/auth-jwt` package tests.

Read the complete
[`auth-jwt-bearer-engine`](https://github.com/vinilana/invokta/tree/main/examples/auth-jwt-bearer-engine)
example for the composition root, the key-set location, and the tests.
