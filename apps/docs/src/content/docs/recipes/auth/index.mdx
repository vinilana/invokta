Invokta ships no identity system. The MCP HTTP adapter accepts a pluggable
`authenticate` hook that turns a verified request identity into the minimal
`Principal`, and the core applies each capability's `access` rule on every
channel. These recipes show where your existing provider plugs into that
boundary. Each one is backed by a runnable, offline-tested example in the
repository.

## Choose a surface

| Callers reach the engine through | Use |
| --- | --- |
| MCP HTTP with bearer tokens from a hosted issuer | The [JWT bearer recipe](/recipes/auth/jwt-bearer/), then your provider's recipe below |
| MCP HTTP from services and automations without a user | [API keys](/recipes/auth/api-key/) |
| Your own application process that already resolved a session | The embedded pattern in the [Auth.js](/recipes/auth/authjs/) and [Better Auth](/recipes/auth/better-auth/) recipes |
| An OAuth-capable MCP client that discovers your Authorization Server | [MCP OAuth discovery](/recipes/auth/mcp-oauth-discovery/) |

Authentication proves who is calling and produces a `Principal`; whether that
principal may execute a capability stays a domain decision. Pair any recipe
here with [domain authorization](/recipes/domain-authorization/) and the
[HTTP authentication guide](/guides/http-authentication/).

## Rules every recipe follows

- The provider SDK or verification library stays at the composition root;
  capabilities see only `Principal`.
- The hook returns a `Principal` for a valid credential, `null` for any
  invalid one, and throws only when verification infrastructure fails.
- Principals carry verified, authorization-relevant claims — never the raw
  token, a full claim dump, or live SDK objects.
- Tests run offline: JWT recipes generate a local key pair and JWKS with
  `jose`, so signature verification is real without any network.
